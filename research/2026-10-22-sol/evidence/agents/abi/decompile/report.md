ArcCore 1.170.0 preserves the previously measured declared ObjC surface, but compatibility also requires reproducing callback ownership, weak delegate behavior, error conversion and selected scheduling rules. This stage resolves several of those rules against actual engine bodies, app callsites and bounded binary inspection. It does **not** establish a complete ABI specification, replacement-engine correctness or a maintenance effort estimate.

The strongest new results are: `_CallWithEHFrame` really has a custom exception frame beyond its tiny pseudocode body; delegate removal differs between subsystems; navigation policy is synchronous and range checked; DevTools callbacks carry either message or error objects and own copied callback storage; and filename selection has an important callback omitted from the function export. [contracts.tsv](contracts.tsv) contains 14 bounded findings with engine, app and primary-source anchors. Initial evidence remains intact under `../initial/`.

The scope was checked against `inputs/context/ENGINE.md` sections 2 and 5.3, `lead-review.md`, both completed extra-batch manifests/READY files and the handoff closure. The current inventory is **199 unique shards**, **567,959 function headers**, and **79 failure placeholders**. All three manifests and all 199 shard hashes were verified. A failure placeholder is not automatically a timeout. All **834 imported-class method declarations** now have exact body headers, including the 16 absent from the initial snapshot. This is availability, not semantic review or app usage. The 63 imported classes / 834 declarations remain the initial declared-surface measurement; no new count of class-confirmed app calls is claimed. See [corpus-inventory.tsv](corpus-inventory.tsv), [initial-requests-resolved.tsv](initial-requests-resolved.tsv) and the initial report.

All engine addresses below are unslid low Mach-O VAs in `ArcCore-1.170.0.arm64`; app addresses are unslid `0x100...` VAs in `Arc-1.168.0.arm64`. Binary reads translate through each image's segment mappings. [selected-bodies.tsv](selected-bodies.tsv) records exact original shard, byte range and hash; [selected-source-lines.tsv](selected-source-lines.tsv) records original header lines. The 36 copied bodies are complete text extracts, each below the 32 KiB extraction cap. Six other selected targets have no exact exported header. [binary-instructions.tsv](binary-instructions.tsv) records instructions and mapped file offsets separately from pseudocode.

`_CallWithEHFrame` is a synchronous block invocation with an unwind contract. The export at `0x441d770` branches to `0x2e0238`, now available in `inputs/decompile-extra/batch-60e9f287fbfb43c6985744de1f22c196/0x2.c`. Its six ordinary instructions load the block invoke pointer at `x0+16`, call it and return; they perform no block retain/copy/release. App callers `0x1001066ec`, `0x100106810` and `0x100106c60` copy a block, call the import at `0x100106798`, `0x10010692c` and `0x100106dd0`, then release it (`inputs/app168/ghidra/decomp/0x1001.c:5367,5422,5598`; copies in [app-selected.c](app-selected.c)). This supports borrowed block lifetime across this synchronous call.

Its 24-byte pseudocode header misses the landing pad at `0x2e0250`. The compact-unwind entry points to an FDE at `0xd81603c` covering **32 bytes**. The CIE at `0xd816020` resolves through pointer slot `0xd824008` to personality `0x83af738`. That personality tests action bit 0, returns literal 5 on that branch, and otherwise tail-branches to `0xc4496a8`. This agrees with Chromium's special frame pattern: `base/apple/call_with_eh_frame_asm.S:23,51–84` and `call_with_eh_frame.cc:19–43`, pinned to **d0c02bfad08ec92a6ffcf989e53cd995e6381a4c**. The source explains search termination at this frame; the binary corroborates the frame, LSDA, landing-pad pattern and search-phase branch. The non-search target has not been independently symbolically named, and no runtime throw test was performed. A plain forwarding call would lose evidenced unwind metadata. [ehframe-unwind.json](ehframe-unwind.json), [tools/unwind.py](tools/unwind.py) and the binary evidence preserve the exact bytes.

Delegate registration cannot use one generic nil-unregister rule. Downloads category `setDelegate:` (`inputs/decompile/0x40.c`, `0x4041fec`) takes a cleanup-only path for nil: instruction `0x4042030` branches past the weak-target update and bridge installation. A non-nil replacement updates the existing target through `_objc_storeWeak` at `0x4042068`. First registration builds weak delegate/context references; destructor `0x4042a20` destroys those weak slots. Context category `setDelegate:` behaves similarly (`inputs/decompile/0x43.c`, `0x43ed9a8`, nil branch `0x43ed9e8`, weak store `0x43eda20`). App registration is visible in caller `0x1004aefe4` (`app168/.../0x1004.c:130065`), with context `setDelegate:` at `0x1004af094`, downloads getter at `0x1004af100` and downloads delegate setter at `0x1004af114`. The static finding is that nil does not clear the existing registration in these two setters; teardown and target expiration remain separate questions.

Navigation is different. `ArcWebContents::setNavigationDelegate:` (`inputs/decompile/0x44.c`, `0x4440dec`) uses weak references to both wrapper and delegate, but its nil path calls native setter `0x4375b40` with zero arguments in `x1/x2` (`0x4440fa8–0x4440fb0`). The native body (`inputs/decompile/0x43.c`, `0x4375b40`) clears its stored pair at offsets `0x3a8/0x3b0` and releases the previous weak-control reference. The nil branch reads the wrapper's existing bridge getter; it does not call the wrapper bridge setter with nil. Thus this clears native registration without proving destruction of the wrapper-held bridge or cancellation of previously queued work. App caller `0x10053b870` dispatches registration at `0x10053b8e0` (`app168/.../0x1005.c:48799`; typed-field context retained in the initial boundary table).

Navigation policy must return synchronously. Engine bridge `0x4445a58` (`inputs/decompile/0x44.c`) loads the weak receiver/context through `_objc_loadWeakRetained`, constructs `ArcNavigationAction`, sends `webContents:decidePolicyForNavigationAction:` at `0x4445abc`, and immediately tests the returned `x0`. The unsigned comparison against 12 accepts **0–11** and traps for everything else, including negative signed representations. App callback `0x100535984` declares `q32@0:8@16@24` and calls `0x10053605c`; its helper `0x100536028` reads an app mapping table for some values (`app168/.../0x1005.c:44808,45079,45092`). No async completion appears at this bridge boundary. Policy names remain unresolved. Pinned Chromium `ui/base/window_open_disposition.h:8–38` currently has 13 ordinary enum values, including `NEW_SPLIT_VIEW`; the range alone cannot justify assigning those ordinals to Arc's twelve accepted values. [binary-selectors.tsv](binary-selectors.tsv) independently decodes the selector reference.

Filename selection is a real callback missing from exported function boundaries. Downloads bridge vtable slot `0xdd2bfe0` points to **`0x4042728`**, between exported bodies in `0x40.c`. Binary inspection resolves its send at `0x404281c` to `browserContext:onDeterminingFilename:defaultFilename:completionTimeout:completion:` via selector reference `0xe28ca48`. It loads weak target/context references, converts a native unsigned 32-bit integer into a double (`ucvtf d8,w24` at `0x40427b0`), places the value in `d0`, and passes a stack completion block whose invoke address is **`0x40428ac`**. That adapter converts the received object through `0x3b60ee8` and invokes captured native callback storage. Neither address has an exact exported header, despite the shard being present. [binary-pointers.tsv](binary-pointers.tsv) and the bounded `0x4042728` binary range preserve the evidence.

The app implementation is independently declared as `v56@0:8@16@24@32d40@?48` at `0x1004e9748` (`app168/.../0x1004.c:182611`). It copies the completion block and routes into `0x1004e9ac4` (`:182794`). If the app bridge's own weak delegate is absent, that helper immediately invokes completion with the default filename; `0x1004e9da8` bridges a chosen Swift string and invokes the block later. This proves an app-side fallback and the completion's single object argument. It does not prove the engine's timeout units, default duration, late-completion behavior or exactly-once guard. An expired engine-side weak receiver is also distinct from the app bridge's weak delegate being absent.

Termination blocks are owned beyond the caller's temporary copy. `ArcBrowserApplication::tryToTerminate:` (`inputs/decompile/0x43.c`, `0x43e6ee0`) calls `_objc_retainBlock` at `0x43e6f1c` and passes callable storage into native `0x42b2430` (`inputs/decompile/0x42.c`). On the first initialized termination path, native code stores the callable in application state; later attempts have an explicit already-terminating path. Callable copy/destructor functions `0x4044e80` and `0x4044ec0` (`inputs/decompile/0x40.c`) retain the block and release it, operations hidden by pseudocode injections but present at binary `0x4044ea0/0x4044ed8`. Missing-header invoke adapter `0x4044e30` accepts `w1<3`, zero-extends it into `x1`, and tail-calls the block's invoke pointer. The immediate method return remains unsigned `Q` per metadata. App caller `0x1004ae4a0` copies/releases its completion around call `0x1004ae53c` (`app168/.../0x1004.c:129535`). Enum names and eventual exactly-once invocation are still unproven.

DevTools's callback ABI is narrower and clearer than Ghidra's recovered prototype. `ArcWebContentsDevTools::openProtocolConnection:error:` (`inputs/decompile/0x44.c`, `0x4415b60`) has metadata `@32@0:8@?16^@24`. Binary `0x4415b74` saves **x3** as the error-out pointer, later passed to `0x4402548` at `0x4415c18`; the apparent extra pseudocode argument is spurious. Success creates `NSNumber` with `numberWithInt:`; failure returns nil. Its missing-header callback adapter at **`0x4416690`** invokes the block as `(block, nil, NSError)` on the error branch (`0x44166e0–0x44166f0`) or `(block, NSString, nil)` on success (`0x441675c–0x441676c`). App open caller `0x1004f285c` uses call `0x1004f2914`, converts NSError on nil and captures the returned handle; its block invoke `0x1004f2640` bridges the first argument to an optional Swift string and forwards the error (`app168/.../0x1004.c:190064,190213`). Runtime receiver identity of this app open call remains limited by the original static flow analysis.

Native DevTools open `0x4355df8` (`inputs/decompile/0x43.c`) checks feature availability and associated WebContents, increments a per-object integer handle, and stores the client in a map. Close `0x4356754` removes the matching entry and invokes destruction through `0x435d09c`. The destruction path `0x435c74c` queues a “DevTools connection closed” status before resetting the original callable. Notification helper `0x435c8fc` puts a copied callable into an owned task; `0x435ca2c` invokes that task's callable. These bodies and shared block copy/destructor operations establish ownership after return and show why already queued callbacks need separate treatment from object deletion. No handle wraparound or reuse guarantee is inferred.

A source-backed mapping is available for the native client: vtable `0xda804e0` has destructor/destructor/message/closed slots pointing to `0x435c3d8`, `0x435c478`, `0x435c51c`, `0x435c6f4`. The latter two bodies match the arguments and roles of pinned Chromium `content/public/browser/devtools_agent_host_client.h:24–31` (`DispatchProtocolMessage` and `AgentHostClosed`). This is a high-confidence semantic mapping, supported by both slot ordering and behavior, not a binary-identity claim. Incoming dispatch `0x435c51c` allows up to **8 MiB** and schedules closure for larger messages; native send `0x43564d8` also has an 8 MiB guard and other checks. Merely exposing upstream CDP would not reproduce all of these Arc bridge rules.

Error conversion is concrete: `_ArcErrorDomain` at data VA `0xdf6bb28` points to CFString `0xe2449f8`, whose 22-byte contents are **`company.thebrowser.Arc`**. Constructor `0x44025f4` (`inputs/decompile/0x44.c`) translates native status codes through table `0xc9d8148` and builds NSError with that domain and `NSLocalizedDescriptionKey`. The byte evidence is in [error-domain.json](error-domain.json). The complete status catalog was not reconstructed.

Two boundaries remain deliberately unresolved. First, downloads pause/cancel/resume (`inputs/decompile/0x44.c`, `0x442fd80/0x442fdd8/0x442fe38`; app calls `0x10052d210/0x10052d034/0x10052d408`) guard wrapper/native state before virtual actions. Cancel forwards its boolean; resume does not explicitly pass a boolean before its tail call. Pinned Chromium `components/download/public/common/download_item.h:198–215` declares `Resume(bool user_resume)`. Without independently identifying this engine vtable, selector resemblance is insufficient to call that stock API slot directly. Second, DevTools notification and download initial-list code (`0x435c8fc/0x435ca2c` in `0x43.c`, `0x42df994` in `0x42.c`) construct queued tasks using a TLS-derived runner, but its identity is unresolved. The app's `0x1004f2a24` routes through current-main-executor checking helper `0x1004ec75c` (`app168/.../0x1004.c:190285,184992`). That is an app expectation, not proof that every engine callback runs on main or that the check performs a scheduling hop.

The handoff closure is useful as a starting index, but its size calculation is unsound. Independent audit reproduces **5,846 names**, consisting of 1,378 `arc-objc`, 524 `arc-path`, six export seeds and 3,938 callees, at depths 0/1/2 = 1,908/1,558/2,380. The supplied script (`inputs/claude-handoff/scripts/arc_layer.py:28`) strips all trailing selector colons before storing bodies, whereas its size dictionary keeps original names (`:15–17,59`). This creates **524 zero-size rows**. Applying that documented normalization resolves all names to metadata, but eight normalized names have multiple entries, producing **5,859 candidate records**. A dictionary keyed by name also silently overwrites those bodies. Categories do not satisfy the initial `^Arc...::` seed regex (`:38`); only another seed condition or a matching direct call can bring them in. Its call regex (`:45`) follows only direct-looking `FUN_...(` calls and misses address-taken `LAB_...` callbacks, virtual calls and dynamic sends. The missing-header callbacks above are concrete closure blind spots.

[closure-audit.tsv](closure-audit.tsv) retains name ambiguity, normalized/original names, metadata/export sizes and availability. **1,196 candidate records** disagree between saved metadata body size and export header size. Neither value is a contiguous byte map. The known malformed `FUN_0421f778` is excluded from semantic/code-volume conclusions. A separate streamed interval audit detects **nine additional regions of at least 1 MiB** that are unusable as contiguous function ranges. For example, metadata `FUN_002b7940` claims `0x2b7940–0x8b5e074`, containing 371,256 other metadata starts; `FUN_059f8a80` claims `0x59f8a80–0x5d6aa50`, containing 9,446. [malformed-region-candidates.tsv](malformed-region-candidates.tsv) lists all ten regions. These are boundary-corruption candidates, not proprietary-code measurements. Min/end overlap flags do not themselves prove any particular small body is malformed. No closure size sum, unmatched-function count, or absent source path is used to estimate Arc-specific code volume.
