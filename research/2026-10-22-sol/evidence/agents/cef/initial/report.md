**CEF route assessment for Arc app 1.168.0 arm64 and ArcCore 1.170.0 / Chromium 156.0.8078.48.** Research and metadata analysis only; no product implementation, builds, or runtime compatibility tests. An exact-version CEF source target exists. The evidence does **not** yet establish that CEF can preserve Arc's native embedding, profile services, or callback contracts. Those are the main route-selection gates.

**Inventory and call evidence.** `tools/inventory.py` reads arm64 Mach-O segment mappings, ObjC class and category lists, metaclasses, relative method lists and chained pointer fixups. It obtains selector and encoding from the binary rather than pairing dyld and otool rows by position. Each imported entry is keyed by explicit class, category, kind and selector. All 834 IMPs match the 1.170 dyld dump and exact Ghidra function starts. Their class/category/kind/selector set also matches 1.168. The inventory independently agrees with `../abi/initial/contract.tsv` on all 834 current encodings and IMPs; that contract marks 828 encodings unchanged and six unknown across versions. This report does not convert those unknowns into compatibility claims.

There are 48 category methods and 105 `.cxx_construct`/`.cxx_destruct` entries. In particular, base and `Extensions` category versions of `ArcBrowserContext::{id,metrics,extensions}` must remain separate. `id` has base IMP `0x4084dc0` and category IMP `0x43f541c`, both in ArcCore 1.170's unslid engine VA basis. Ghidra names have the `Class::selector` form. An exact start match does not make Ghidra min/end bounds contiguous body-byte coverage; no interval size or unmatched-function count is used to estimate proprietary code here.

The engine metadata also contains **1,964 methods on 146 Arc-prefixed classes**. The additional 83 classes are outside the 63-class imported inventory, not proven unreachable. Factories/accessors return objects such as `ArcBrowser`, `ArcWebContents`, history and extension service wrappers even when the app has no class-symbol import for them. [evidence/engine-objc-all.tsv](evidence/engine-objc-all.tsv) retains the broader metadata; the route-gating request list includes relevant returned classes. A complete reachable contract requires following those returns, delegate protocols and app dispatches.

The supplied import list also contains four non-class symbols: `_arcCategoryEnabledFlag`, `_ArcErrorDomain`, `_CallWithEHFrame` and `_emitTraceEvent`. They are outside this selector inventory and still belong to the replacement engine's ABI requirements. Public CEF method coverage alone does not supply the required Arc class names, exported symbols or native value layouts.

**Runtime, embedding and ownership constraints.** CEF's [architecture documentation](https://github.com/chromiumembedded/cef/blob/426920c33ef22551e0b8f48cf343d623ac25642d/docs/architecture.md#L140) distinguishes runtime bootstrap from browser/window style: Alloy bootstrap was removed in M128, while Alloy **style** remains under Chrome bootstrap. [cef_types_runtime.h](https://github.com/chromiumembedded/cef/blob/426920c33ef22551e0b8f48cf343d623ac25642d/include/internal/cef_types_runtime.h#L39) supports mixed styles but says windowless rendering always uses Alloy. Chrome style offers more default Chrome functionality; Alloy provides additional client callbacks and windowless rendering. Neither name alone proves the Arc service contract.

On macOS, [cef_types_mac.h](https://github.com/chromiumembedded/cef/blob/426920c33ef22551e0b8f48cf343d623ac25642d/include/internal/cef_types_mac.h#L151) says supplying `parent_view` forces Alloy style. `CefWindowInfo::SetAsChild` supplies that parent NSView. Arc exposes native pane creation, attachment, detachment, reparenting and delegates. The arrived engine pseudocode confirms a concrete `WebContentsPaneHostView` class and subview attachment, but full native-view/compositor equivalence remains unverified. The critical question is whether CEF can preserve this host arrangement and required browser services together. A Views-hosted Chrome window is an alternative to investigate, not an established substitute for Arc's NSView contract. Historical wording elsewhere in the docs does not override these current platform headers.

The [macOS app protocol](https://github.com/chromiumembedded/cef/blob/426920c33ef22551e0b8f48cf343d623ac25642d/include/cef_application_mac.h#L83) requires an NSApplication subclass implementing `CefAppProtocol`, including send-event state. The pinned [cefsimple_mac.mm](https://github.com/chromiumembedded/cef/blob/426920c33ef22551e0b8f48cf343d623ac25642d/tests/cefsimple/cefsimple_mac.mm) shows initialization, orderly Cocoa termination and shutdown. `CefInitialize`/`CefShutdown` run on the main application thread; the separate `multi_threaded_message_loop` setting is supported only on Windows/Linux ([cef_types.h](https://github.com/chromiumembedded/cef/blob/426920c33ef22551e0b8f48cf343d623ac25642d/include/internal/cef_types.h#L246)). External pump integration is documented, with scheduling requirements, but Arc's existing event-loop ownership is unknown. A framework replacement also needs a compatible helper/bundle/bootstrap arrangement.

CEF reference-counted interfaces are not Arc's ObjC ARC objects or encoded `std::optional<arc::...>`/`shared_ptr` value layouts. Some APIs return borrowed callback objects; [download callbacks](https://github.com/chromiumembedded/cef/blob/426920c33ef22551e0b8f48cf343d623ac25642d/include/cef_download_handler.h#L127) explicitly prohibit retaining `CefDownloadItem` outside the callback. A durable `ArcDownloadItem` needs copied state plus a separately managed action callback. Cookie visitors run on UI; URL requests and their callbacks stay on the creating CEF thread; content-setting APIs require browser UI. Arc block retention, Swift executor delivery, cancellation races and delegate destruction cannot be inferred from ObjC encodings. The mappings preserve these unknowns.

CEF is a plausible backend for the cited public-operation subset. Choosing it now would assume answers to native embedding and Chrome-service access questions that the evidence does not supply. A custom in-tree `arc/` layer has a clearer path to real Chrome profile/browser services, but exposes maintenance to changing Chromium internals and still requires every Arc ABI/callback contract. Neither route is established as cheaper or complete. If further decompile analysis identifies mostly forwarding to stock Chrome services, an in-tree bridge becomes more credible. If required behavior fits documented CEF operations and native hosting without private-service access, the CEF route becomes more credible. If a CEF route needs custom libcef patches, those patches become an additional Chromium/CEF rebase surface rather than disappearing work.
