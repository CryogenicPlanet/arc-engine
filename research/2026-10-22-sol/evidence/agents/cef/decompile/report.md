**CEF route assessment, second stage — Arc app 1.168.0 arm64 / ArcCore 1.170.0 / Chromium 156.0.8078.48.**

The new evidence favors an in-tree Chromium bridge as the route to investigate for preserving the existing Arc interface. Actual Arc entry points reach Chrome profile creation, omnibox providers, Web Store installation, extension toolbar state and password-save controllers. Native pane attachment also reaches content compositor internals. A CEF implementation would need to reproduce these contracts, find equivalent public operations, or maintain libcef changes. This is a route recommendation for further research, not proof of CEF impossibility or a measured implementation estimate.

The previously missing four backend targets are available. Their identities can now be supported by source strings and call patterns. Remaining blockers concern behavioral substitution, native hosting and callback delivery, rather than merely the presence of Chrome-related names.

The Web Store unattended branch can be narrowed further. At `0x42e6790`, unattended construction passes a null native window, replaces the constructor-installed vtables, and clears the byte initialized as post-install UI enabled. [installer-vtables.tsv](evidence/installer-vtables.tsv) independently decodes Mach-O pointers: primary tables `0xd9a2988` and `0xda7dfc0` differ at slots 9 and 11. Slot 9 changes from the small prompt allocator `0x786cf44` (`extra/0x78.c`) to the return-zero body `0x614600` (`extra/0x6.c`). The source hook describes null `CreateInstallPrompt()` as no prompt; `webstore_standalone_installer.cc:136` accepts that path without showing install UI. This supports a prompt-suppression interpretation. Slot 11 changes `0x786cf60` to `0x4315348`; neither has an exact exported body. Full custom install-UI behavior, policy outcomes and the complete vtable identity remain unresolved. No live installation was performed.

**Native hosting is a stronger gate than a generic NSView wrapper.** App BL `0x1005426b4`, [caller 0x1005426a0](evidence/app-1005426a0.c), calls `createPaneHostView` on the saved `WebContentChromium::webView` field. The engine IMP `0x4410bb4` has no exact export, but its binary word `0x140ca14a` branches to [0x47390dc](functions/47390dc.c), which creates `WebContentsPaneHostView` (`base/0x47.c`). Thus this omitted four-byte thunk is resolved and is not an outstanding shard request.

The path `0x4376580` → [0x473c4dc](functions/473c4dc.c) wraps the underlying native view in `WebContentsHostView`, constrains all four anchors and installs a weak observer (`base/0x43.c`, `base/0x47.c`). [0x473c9a8](functions/473c9a8.c), [0x473cad8](functions/473cad8.c), [0x473cf0c](functions/473cf0c.c) and [0x473d7e4](functions/473d7e4.c) explicitly inspect that host's known subview and `ViewsHostable` protocol before accessing Chromium-side view state. On attachment, [0x4737eb4](functions/4737eb4.c) checks `ArcMacCoalescedResizing`, detaches/replaces subviews and synchronizes geometry/display state. When replacing hosted contents it calls `0x473cad8`, which can reach [0x6846c88](functions/6846c88.c) (`extra/0x68.c`). Source identity does not prove that all compiled behavior is unchanged. The old initial report's generic layout uncertainty is now a concrete internal-view/compositor dependency.

CEF's pinned [`include/internal/cef_types_mac.h:151–152`](https://github.com/chromiumembedded/cef/blob/426920c33ef22551e0b8f48cf343d623ac25642d/include/internal/cef_types_mac.h#L151) forces Alloy style when `parent_view` is provided. Wrapping a native CEF view alone does not demonstrate them. No direct BL to the inspected `attachToPaneHostView:` stub was found; indirect/thunk attachment and runtime hosting were not tested.

**Callbacks and ownership: narrower positive evidence.** Profile wrapper `0x43e8368` captures the ObjC completion in heap state; backend `0x42b3d74` copies the name/callback binding and captures a weak-reference control structure. It rejects empty names and null callbacks. Stock profile creation distinguishes initialized and created callbacks, runs from a UI-thread entry point, and records hidden profiles as ephemeral/omitted (`profile_manager.cc:1037–1102`). Arc passes its binding as the initialized callback and null as the created callback at `0x42b3d74`. This does not establish Arc type=1 semantics, existing-profile migration or a Swift executor guarantee.

The bound completion [0x42b3f34](functions/42b3f34.c) (`base/0x42.c`) emits `failed to create profile on disk` on null profile, otherwise constructs the context result and invokes the stored callback. Its destructor [0x42bf5ac](functions/42bf5ac.c) releases captured callback/name/weak state. The ObjC invocation adapter is referenced as `LAB_043eb7a0` and has no exact body export. This leaves exact block invocation, NSError conversion and executor delivery open despite resolving the profile backend.

Extension backend `0x42e6790` accumulates callbacks in per-install state; [0x42e712c](functions/42e712c.c) (`base/0x42.c`) maps a result through a table, invokes the registered callbacks, then removes the state. Stock `BeginInstall` explicitly adds a lifetime reference released by cleanup (`webstore_standalone_installer.cc:54–57`). This identifies lifetime and fan-out work for a replacement. It does not establish the Arc result enum, all cancellation races or the ObjC adapter `LAB_043fec84`. Browser autocomplete's stored completion and `LAB_043e5fd4` likewise require recovery. Pseudocode ARC-injection annotations alone do not certify retain counts or Swift actor delivery.

**Closure and malformed-region audit.** [closure-audit.tsv](evidence/closure-audit.tsv) reproduces the handoff's 5,846 unique historical names: 1,378 `arc-objc`, 524 `arc-path`, six exports, and 3,938 anonymous callees. Depths are 1,908 seeds, 1,558 at depth one and 2,380 at depth two. No historical name is unmatched after reproducing the script's trailing-colon normalization. Eight names map to multiple metadata entries, yielding 5,859 address candidates, not 5,859 certified Arc functions. For example `ArcBrowserApplication::init` conflates `init` and `init:`. Several duplicate names also identify omitted thunks.

Review of `inputs/claude-handoff/scripts/arc_layer.py` establishes limitations beyond counts: it keys bodies/sizes by name, strips trailing colons, follows only `FUN_XXXXXXXX` followed by `(` for two levels, does not follow address-taken callbacks or `LAB_` entries, and does not stop at source-backed stock functions. Its `^Arc...::` seed rule misses `objc::Categories::...` names unless another seed condition happens to match. The shared getter above also illustrates how an actual Arc IMP can have a non-Arc alias. This is a useful bounded index, not a complete Arc ownership boundary or proprietary-code measurement. Source-backed stock functions reached here are controls against treating every closure member as proprietary.

`FUN_0421f778` is excluded from size/semantic attribution. [malformed-regions.tsv](evidence/malformed-regions.tsv) also detects nine other metadata bodies over 1 MiB. All ten have major disagreement between saved metadata sizes and current export-header sizes. Additional suspect body regions include `0x2b7940` (`batch-60e9f287fbfb43c6985744de1f22c196/0x2.c`) and `0x16220b0` (`base/0x16.c`): bounded text reads contain far-separated jump/unreachable-block addresses and problematic jump-table recovery; saved spans encompass hundreds of thousands of other starts. Prefix excerpts are preserved separately. These are boundary-recovery exclusions, not identified Arc modifications. A size threshold or overlap alone does not prove every exported operation is corrupt. No TSV size sum, stock-match deficit or closure byte total is used here.

**Remaining specific work.** [additional-shards.tsv](additional-shards.tsv) lists five exact targets without exact-start exports: profile callback `0x43eb7a0`, extension callback `0x43fec84`, browser autocomplete callback `0x43e5fd4`, and normal/custom installer UI targets `0x786cf60` / `0x4315348`. Next questions are concrete: Can public CEF operations reproduce these named-profile and omnibox contracts while preserving existing storage? Can Alloy parent-view hosting reproduce the measured pane/compositor behavior? What do the three ObjC callback adapters do on success, failure, destruction and replacement? What are the unattended vtable overrides' complete effects? Required follow-up should include runtime behavioral comparisons on the parent-controlled Mac; none was performed here. This stage also does not establish helper/bootstrap compatibility, passkey completeness, existing profile encryption, renderer IPC equivalence, older engine behavior or libaperitif semantics.
