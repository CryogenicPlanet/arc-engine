# Matcher second stage: source-backed names and bounded behavior

The useful result is a set of reviewable Chromium correspondences and Arc integration seams, **not a proprietary-code percentage or a rewrite-size estimate**. Eight anonymous functions have strong source-backed identities in the inspected regions. Two additional comparisons identify a GPU extension candidate used by full-page capture. A native-host tail branch resolves an apparent missing method without another decompile. The original 5,846-row closure omits declared Arc methods and contains name/size artifacts; its byte sum is unusable.

This is research only. Initial evidence under `initial/` is unchanged. No engine implementation, build, remote-machine access, package installation, messaging, or external mutation was performed.

**Evidence identity and scope.** Engine addresses below are unslid ArcCore **1.170.0 arm64** VAs; app addresses are from the separate **1.168.0 arm64** executable/pseudocode. Chromium references use the supplied primary-source mirror at **d0c02bfad08ec92a6ffcf989e53cd995e6381a4c**, version **156.0.8078.48**. [source-references.tsv](source-references.tsv) records exact paths, pinned URLs, and SHA-256 hashes for 12 files. Missing files elsewhere in that partial mirror are not treated as absence evidence.

The engine SHA-256 was rechecked against [initial/images.json](../initial/images.json): `69276adaca785a46f2554e7fd18926e7fcdd6aba44ba64400a337427817db3dd`. No new whole-image stock-binary matching was attempted. The stock build's optimization/link differences remain relevant limitations.

All 199 manifest entries across base `inputs/decompile/` and both completed immutable `inputs/decompile-extra/batch-*/` batches passed streamed size/SHA-256 verification: 1,114,106,346 C-file bytes. The supplied `claude-handoff/scripts/arc_layer.py` calls `rstrip(":")` on names and keys both bodies and sizes by name. Consequently `ArcBrowserApplication::init` at `0x43e6538` and `init:` at `0x43e6548` collapse into one key. Removing selectors' final colons also breaks size lookup for many parameterized methods. The reconstruction preserves exact names/addresses and excludes the known malformed seed before traversal. It leaves out 398 addresses represented in the original handoff and adds none. This difference reflects that bounded parsing rule and exclusion, not 398 non-Arc functions.

The reconstruction deliberately retains the handoff's narrow call rule: literal anonymous `FUN_…(` calls, two levels only. It does not discover ObjC dispatch, virtual calls, stored callback addresses, most named callees, or all thunks. It is not an exhaustive reachable interface or a corrected complete Arc closure. [reconstructed-closure.tsv](reconstructed-closure.tsv) and [reconstructed-edges.tsv](reconstructed-edges.tsv) make those boundaries explicit.

Independent parsing of the **1.170 dyld metadata**, preserving class, selector, `+`/`-`, and category, finds **1,964 declared method rows on 146 Arc-prefixed classes**, including 143 category rows, at 1,566 distinct implementation VAs. These are metadata counts, not exported-class counts or app-called methods. Of those rows, **330 at 184 distinct VAs are outside the handoff address set**, including methods with available bodies. [objc-closure-audit.tsv](objc-closure-audit.tsv) contains all identities and inclusion decisions. Thus neither the old 1,378 named seeds nor the reconstructed 1,379 named seeds covers the declared Arc interface.

For example, dyld lines 3150–3157 identify base `-[ArcPermissionRequest additionalData]` at `0x2d0fb40`; the indexed body is named [WebNNMLFeatureProvider::featureNames](bodies/0x2d0fb40.c) and simply loads an object field. Both VAs are outside the handoff. The category has a different implementation; the base address has a shared/chosen Ghidra symbol identity. Neither may be inferred from the other. This is not a conclusion about runtime category precedence, callback ABI, or which receiver a particular app message reaches.

* App [0x1004ae240](/home/exedev/work/inputs/app168/ghidra/decomp/0x1004.c:129408) calls the `run` selector after the Arc application getter. The constructor and UI-update examples disprove a simple “function contains an `arc/` path, therefore proprietary function” classifier. A Chromium-owned function can contain inlined Arc UI implementation code. Conversely, `BrowserActions` and command-action updater selection already occur in pinned upstream `browser_command_controller.cc:2853–2862`; seeing those names in Arc does not prove TBC added them. Inlining, devirtualization, template expansion, assertion configuration, and ordinary build variation remain explanations for many binary differences. These examples do not assign the observed behavior to a specific edited source file.

There is a concrete **guard-comparison candidate** at `0x16b9d84`: after obtaining a tab-like object, the exported body calls the indexed `0x27de0` search and rejects `-1`. Pinned `ScheduleUIUpdate` instead rejects absent `TabInterface` or a mismatched `GetBrowserWindowInterface()` result (`browser_ui_controller.cc:120–124`). The remainder has strong role agreement. This structural predicate difference should be checked against coherent disassembly and transient tab-detach behavior before calling it a semantic modification; the two guards may agree for normal states.

**Full-page capture exposes a bounded extension candidate.** App [0x10053f348](/home/exedev/work/inputs/app168/ghidra/decomp/0x1005.c:50836) directly calls `captureFullPage:` with a block; a second call is recorded at `0x10054336c`. `0x435da28` supplies location **`GetMaxTextureSize`, `../../content/public/browser/gpu_utils.cc`, line `0x9d`**, captures callback state, and calls identified `GpuProcessHost::CallOnUI` with kind `1`, force-create `0`. Its bound callback entry [0x40bf0c8](bodies/0x40bf0c8.c), shard `0x40.c`, checks `gpu_host_`, accesses a service, and forwards the captured callback via virtual slot `+0xd8`. This is positive engine code and call-context evidence for a texture-size preflight integrated with full-page capture. The **complete supplied pinned files** `content/public/browser/gpu_utils.cc`, `.h`, and `content/browser/gpu/gpu_process_host.cc`, `.h` contain no `GetMaxTextureSize` helper. Their hashes and absence assertions are retained. This is a focused **candidate extension to upstream GPU plumbing**, stronger than absence of a source path or unmatched machine bytes. It does not recover the helper's exact signature, prove the location string's source provenance, name the service slot, or establish the callback's thread/ownership semantics. It therefore does not establish an exact upstream patch or a CEF route blocker.

[saved-span-outliers.tsv](saved-span-outliers.tsv) checks all ten old spans over 1 MiB. Two additional **suspect merged-recovery regions** need quarantine for consequential matching: `FUN_002b7940` (extra `0x2.c`, original byte offset 4,890,401) has a 21,900-byte current header but defined pseudocode labels extending to `0x8b5b918`, alongside unreachable-block and switch-recovery warnings; `FUN_016220b0` (`0x16.c`, offset 831,207) has a 9,416-byte current header but defined labels extending to `0x848e1e0` with unrecovered indirect-jump warnings. Actual AddressSet membership and branch evidence are required. Other large old spans often now export compact call wrappers; old min/end anomalies alone do not prove those current bodies malformed.
