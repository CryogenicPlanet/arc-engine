## Supported lifetime contract and transport lifecycle

Browser is not base::SupportsUserData; its supported generic lookup is `GetUnownedUserDataHost`. The candidate's `SessionsPhysicalCloseData` is owned by the **existing ArcBrowserWindow userdata**, with a `ScopedUnownedUserData` registration on that native host and a weak ObjC observation. The destructor hook only asks the typed host for an existing Data. It never casts an unknown window, creates/relooks-up a canonical ArcBrowser, retains native ownership, uses an unbounded raw-pointer map or posts work.

Installation is inside the existing canonical ArcBrowser initialization path. That initialization already requires ArcBrowserWindow. It occurs before ArcBrowserHolder publication, so the candidate must not call wrapperForBrowser during installation. Current ownership is window → strong ArcBrowserHolder.wrapper → strong associated SessionsBrowserObservation; the new Data → weak observation introduces no cycle or native/facade lifetime extension. Receipt strongly locks only the existing weak observation for the synchronous delivery, with precise ObjC lifetime.

The Data consumes its scoped registration **before** the app-capable callback and never accesses itself/native/window after that call returns. No independent boolean once guard or guessed original registry skip is added. One typed registration and one physical destructor entry bound this transport. Reentry through the generic hook after consumption sees no transport entry. This is solely transport safety, **not proof of original application-registry idempotence or eligibility**. If the observation expired, consumption still unregisters and ObjC nil receipt does nothing. If this transport was never registered, the hook does nothing; supported native callback eligibility remains unproved for those paths.

If the hook is empty/cleared before destruction, the window-owned Data instead unregisters during synchronous `window_.reset()`. BrowserWindowDeleter calls `DeleteBrowserWindow`; ArcBrowserWindow implements it as `delete this`. Thus window userdata destruction occurs while Browser's host still exists. This explicit reset is essential: Browser declares window_ before its unowned host, so implicit member teardown alone would have the opposite lifetime order. SupportsUserData destroys Data in unspecified order; Data destruction only unregisters/releases its own weak reference, never consults another userdata entry and never notifies. Owning ScopedUnownedUserData on an externally retained ObjC observation would violate this host lifetime contract and is deliberately avoided. Chromium's duplicate typed Set and double Erase are CHECKs; the current canonical one-install association is required, and unsupported duplicate initialization is not newly blessed.
